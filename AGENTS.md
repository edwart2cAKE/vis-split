- `uv run pytest -v` — run tests
- `uvx ruff check .` — lint (no project install needed)
- `uv run basedpyright src tests` — typecheck in strict "recommended" mode (matches Zed); `[tool.basedpyright]` in pyproject.toml points at `.venv`, which also fixes import resolution in Zed
- `uv run python -m autosplitter.main --config configs/your-game.yaml --check` — validate config, print summary; exit 1 + precise error if invalid

- `uv run python -m autosplitter.main --gui` — launch the optional PySide6 GUI (`uv sync --extra gui`)
- `uv run python -m autosplitter.main --config configs/your-game.yaml --probe IMAGE.png` — load image, crop to ROI, print average RGB + suggested YAML snippet for color tuning
- `uv run python -m autosplitter.main --live [SOURCE] [--width W] [--height H] [--max-frames N] [--snap N] [--livesplit] [--loop] [--overlay] [--record PATH] [--config-poll-interval S]` — live capture demo: rolling fps/match/state status; SOURCE overrides `capture.stream_url` and may be a `.ts` file for offline smoke tests or a `udp://`/`srt://` URL (then pass its dimensions via --width/--height, e.g. `"srt://127.0.0.1:9733?mode=listener&rcvlatency=20000" --width 640 --height 360`); `--snap N` saves frame N to snap.png and exits; `--livesplit` forwards split events to LiveSplit Server (and, only with `ocr.mode: undo`, `unsplit` / a late-HUD re-`split`); `--loop` rearms the machine after DONE once the next run's first color stays quiet for `detection.restart_quiet_seconds` (user resets their own timer between runs); `--overlay` shows ROI rectangle + HUD window (throttled ~10 Hz, ESC/q to close); `--record PATH` writes a codec-copy .mkv at full source resolution to PATH while detecting (single ffmpeg process — no second UDP consumer needed); when recording, the detection output is scaled to `capture.width`x`capture.height`, so those may differ from the source; without `--record`, ffmpeg emits source-resolution frames and `capture.width/height` must match the source exactly; Ctrl-C or EOF stops. If `--record` is omitted but a `record:` config section exists, the path is resolved from the config's `path_template` (supports `{game}`, `{date}`, `{time}`, `{datetime}`, `{attempt}` variables). On exit, if `record.convert_to` is set, ffmpeg converts the .mkv to the target format (best-effort, .mkv never deleted).

Verification order per phase: tests → ruff → basedpyright → phase demo command.

## Platform

- Target: Linux (Arch/Wayland) + OBS Studio. Never introduce Windows-only APIs.
- LiveSplit runs under Wine; the detector runs natively on Linux, independent of LiveSplit.
- LiveSplit Server over TCP: `127.0.0.1:16834`.

## Non-negotiables

- All tunables live in your game config (e.g., `configs/your-game.yaml`). Never hard-code resolution, colors, or thresholds.
- ROI coordinates are normalized floats (0.0–1.0) so resolution changes don't break detection.
- Color matching uses configurable tolerance, never exact RGB equality.
- Process only the cropped ROI with vectorized NumPy/OpenCV — no per-pixel Python loops (target ~60 FPS).
- Detection is a state machine (`NORMAL → TRANSITION → WAITING_FOR_RESET`, terminal `DONE`): require N consecutive matching frames before splitting (debounce), use `reset_threshold` hysteresis after a split, and never emit more than one split per continuous transition. Contract: streak counts frames at/above the active split's threshold; clearing is strictly below `reset_threshold`; a frame that clears one split never counts toward the next one's streak. The LAST split skips `WAITING_FOR_RESET` — DONE is entered on the next frame with the index exhausted (so `current_split`/`current_detector` are None even if the victory screen keeps the color lit; a persistent final color must not stall the run). With `start_transition`, its TRANSITION settles through `WAITING_FOR_RESET` but clears WITHOUT advancing the index (the gate precedes splits[0]); `_transition_is_start` tracks which kind of TRANSITION is settling.

## Boundaries

- Keep frame acquisition (`capture/`) separate from detection logic (`detection/`); input source must be swappable.
- Keep all LiveSplit protocol logic inside `livesplit/client.py` (`LiveSplitClient`); the detector only calls methods like `split()`.
- Detector and state machine must be unit-testable from prerecorded frames with no OBS or LiveSplit present (pytest once tests exist).
- v1 ships the color detector only. Do not implement template matching until color detection works.

## Dependencies

Minimal set: OpenCV, NumPy, PyYAML, plus whatever the chosen OBS capture method requires. Do not add frameworks without a demonstrated problem.

## Gotchas

- Capture method (decided after research): OBS sidecar **Recording → Custom Output (FFmpeg)**, container `mpegts`, URL `udp://127.0.0.1:9733?pkt_size=1316` — runs alongside Streaming, pure userspace, no new pip deps (system `ffmpeg` binary decodes to raw BGR24 on a pipe). obs-websocket screenshot polling was rejected (~15-20 fps); virtual cam needs v4l2loopback kernel module. The autosplitter's `--live` is the sole UDP consumer; when `--record PATH` is passed, the same ffmpeg subprocess also writes a codec-copy .mkv at source resolution (no extra socket needed) and scales the detection frames to `capture.width/height` (`-vf scale`).
- For the Custom Output (FFmpeg)/UDP sidecar, pin its **Output (scaled) Resolution to 1920x1080** regardless of canvas (works for both the 1920x1080 and 2560x1440 setups; both are 16:9). `capture.width/height` in config must match it exactly when not using `--record` — a mismatch garbles frames silently and the pipe reader hits EOF (with `--record`, ffmpeg scales detection frames to `capture.width/height`, so a mismatch is tolerated). Receiver-side UDP URLs (config `stream_url`) should only have `pkt_size`; output-only params (`fifo_size`, `overrun_nonfatal`, `buffer_size`) cause ffmpeg to fail when opening the input.
- Sidecar encoder must be H.264 — tick **Show all codecs** in OBS's Custom FFmpeg output or only mpeg2video lists. Video Encoder Settings: nvenc → `bf=0`, libx264 → `tune=zerolatency bf=0`. Do NOT add nvenc `delay=0 zerolatency=1`: measured 10-40s latency regression (reactive CBR pacing). If splits fire late while `--live` fps stays steady ~60, frames are arriving stale from upstream (OBS), not queued in our pipeline (drain would spike fps).
- Latency measurement: stop Recording, send a synthetic clock (`ffmpeg -re -f lavfi -i testsrc=size=1920x1080:rate=60 -c:v h264_nvenc -bf 0 -g 60 -f mpegts udp://127.0.0.1:9733?pkt_size=1316`), run `--live --snap N`, compare snap.png's burned-in clock vs wall time.
- Packet loss is silent: kernel UDP socket buffer overflows before ffmpeg's fifo ring, so missing `Circular buffer overrun` warnings prove nothing.
- Hot loop must stay allocation-free per frame (measured: naive bytearray+copy reader + per-frame `build_detector` capped the pipeline at ~45 fps while a bare `ffmpeg -f rawvideo -pix_fmt bgr24 - >/dev/null` on the same URL sustains 59; fixed consumer paces at 60.1). Invariants: `RawPipeReader` decodes into one reused buffer — the returned ndarray is invalidated by the next read, copy it to retain; `TransitionDetector` builds its `ColorDetector`s once in `__init__`; `ColorDetector` precomputes `cv2.inRange` bounds at construction. Symptom of regression anywhere in this chain: `--live` fps pinned below ~60 with latency climbing steadily.
- Stream rate = OBS's **Common FPS Value** (Settings → Video), not monitor Hz; per-config (all shipped configs are 60 now, incl. `start-powerless.yaml`; double `required_frames` for a 120 fps stream) and must match that config's `capture.fps`. Debounce is frame-counted: keep `required_frames ≈ capture.fps / 20` (~50 ms of flicker immunity). `--live` prints a one-time HINT when a udp/tcp/srt stream's rolling fps deviates >15% from `capture.fps`.
- LiveSplit Server wire protocol: commands case-sensitive, newline-terminated (`split\n`); `split` has NO response, `ping` returns `pong`; server must be started manually per launch (Control → Start TCP Server) unless Startup Behavior is configured. `LiveSplitClient.split()` never raises and never blocks longer than `livesplit.timeout_seconds`; reconnect attempts are rate-limited to `livesplit.reconnect_seconds`. Detection must keep running when LiveSplit is down. Query commands (`getcurrenttimerphase`, `getcurrentsplitname` via `LiveSplitClient.query()`) return the first response line or None on any failure; they can each stall up to `timeout_seconds`, so `_run_live` polls both at most every ~2 s (wall-clock gated) — never per frame. Polling also drives the desync WARN: while LiveSplit reports Running, the desync check is a substring match — it warns only when the detector's expected split name (`machine.current_split.name`) is NOT contained in LiveSplit's segment name, once per distinct pair until they agree again; it is silent when the detector is DONE (no expected split).
- Unsplit rollback (opt-in `livesplit.resync_on_unsplit: true`, default false): the same ~2 s poll also calls `LiveSplitClient.get_split_index()` (`getsplitindex`; -1 valid; `-`, `[Error]` or anything but optional sign + ASCII digits -> None). `query()` drains unread socket bytes before sending so a late reply to a timed-out query cannot be read as the next answer. `TransitionDetector.expected_ls_index` is `_index + 1` in TRANSITION/WAITING_FOR_RESET for a split (not the start gate), else `_index`. `livesplit/sync.py` `UndoWatch` (pure) is ARMED by a Running poll with L == expected (not subject to hold-off), disarmed by any non-Running phase and on `--loop` rearm; only while armed does it confirm an undo: Running, 0 <= L < expected, >= `HOLDOFF_SECONDS` (3.0) since the last fired split, and 2 consecutive polls (`CONFIRM_POLLS`) agreeing on (L, expected). Arming prevents splits fired while the timer was NotRunning plus a late start at index 0 from looking like an undo. An undelivered `split()` suppresses detection (one-line notice) until a poll shows L == expected. Then `rollback_to(L)` (NORMAL/WAITING_FOR_RESET/DONE only; rejected in TRANSITION/WAITING_FOR_START): NORMAL keeps state; the others re-enter WAITING_FOR_RESET with `_transition_is_start=True` (flag now also means 'settle without advance') so a still-lit color must drop below `reset_threshold` first. The detector never writes LiveSplit state. Limits: rollback from DONE is effectively unreachable (without `--loop` the run exits once LiveSplit reports Ended; with `--loop` the rearm after `restart_quiet_seconds` beats the 3 s hold-off plus 2 polls), so final-split undo is NOT supported; a timer reset+restart that lands at index 0 mid-run while armed is indistinguishable from an undo and is treated as a rollback to 0; skipsplit and the GUI worker are not handled; OCR resync and unsplit rollback can disagree and flip-flop (startup WARN if both enabled). Verify `getsplitindex` replies against your LiveSplit first.
- `livesplit.follow_timer` (opt-in, default false; implies undo; `livesplit.poll_seconds`, default 2.0, sets the poll cadence for both modes): increments 1-3 (pause following is the separate opt-in `follow_pause`). `_run_live` uses `_FollowPoller` + `livesplit/follow.py` `TimerFollower` (pure; owns an `UndoWatch`). Poll order: phase (None aborts the poll; NotRunning skips the index/name queries but `observe` still runs so RESET can fire), `getsplitindex` (None aborts), `getsplitcount` once per connection (mismatch with `len(splits)` prints a WARN and disables skip-forward; undo still works), `getcurrentsplitname` only when L != expected or L changed (else cached). Undo works through Paused and from Ended (Ended at L=N=E arms, then Running at N-1 rolls back). SKIP_FORWARD: phase Running/Paused, expected < L <= N-1, state in WAITING_FOR_START/NORMAL/WAITING_FOR_RESET, 2 consecutive polls with identical (L, expected), no hold-off or arming. `TransitionDetector.advance_to(L)` settles like `rollback_to`: WAITING_FOR_RESET with `_transition_is_start=True`, so the target color must read strictly below `reset_threshold` before NORMAL (no re-fire; pending +1 advance cancelled); `index == N` -> DONE; TRANSITION/DONE refused. A manual LiveSplit split looks identical to a skip, and the detector follows it. `getsplitcount` may be unsupported by older servers: then a one-time-per-connection notice is printed, skip-forward stays enabled without validation, and a reconnect re-runs the check (and re-enables skip after a mismatch). An applied action sets `last_split_time`, so the 3 s undo hold-off applies: an Unsplit right after a skip/follow is ignored for ~3 s. A failed poll (phase or index None) clears pending skip/undo candidates so confirmation polls are truly consecutive. `poll_seconds` must be finite and > 0. Increment 2 lifecycle (all behind follow_timer): RESET = phase NotRunning after Running/Paused/Ended was seen (single poll; NotRunning without prior activity, or right after a reconnect, is ignored) -> `machine.reset(settle=True)` (no gate: WAITING_FOR_RESET at index 0 with settle-without-advance so a lit split-0 color cannot fire into an idle timer; with a gate: WAITING_FOR_START) and `last_split_time=None`; MANUAL_START = machine at the start gate and LiveSplit Running/Paused with L >= 0 (single poll) -> `advance_to(L)`, no `start` is sent; RUN_ENDED = Ended with L == N and expected < N, 2 identical polls -> `advance_to(N)` (DONE). A split-count mismatch disables RUN_ENDED and MANUAL_START as well as skip (RESET still works). A RESET while DONE only rewinds with `--loop` (without it the process exits at DONE; undo of the final split is out of scope there). After a RESET with `start_transition.auto_start_timer`, a still-lit start-gate color auto-starts the timer immediately (configured automation); a manual start at the gate does not double-start (the server ignores `start` unless NotRunning). RUN_ENDED (and thus the Ended follow) only fires after the follower has seen the timer Running or Paused since construction / the last `disarm()` / RESET / reconnect, so a stale Ended timer at startup or after a `--loop` rearm is ignored (undo-from-Ended arming does not need it); MANUAL_START also needs L < N. A reset or restart that happens while the splitter is disconnected from LiveSplit is invisible (the follower disarms on reconnect; only the desync WARN fires). Open question for the user: after a RESET with a start gate, a still-lit gate color fires the start immediately (and sends `start` with `auto_start_timer`). The detector never sends reset/pause/resume. `livesplit.follow_pause` (default false, requires `follow_timer`, else ConfigError): PAUSE on the first Paused poll and RESUME on Running (single polls, only while paused); while paused `_run_live` skips `machine.feed_result` (the ratio is still computed for the HUD, the status line shows `FROZEN`; one attribute read per frame), and PAUSE/RESUME call `machine.clear_streak()` so a pre-pause partial streak cannot complete after resume. They do NOT touch `last_split_time` or `undo_suppress` (no hold-off ping-pong). A TRANSITION/WAITING_FOR_RESET machine just stays put while frozen; undo stays armed across Paused. `disarm()` (reconnect, RESET, `--loop` rearm) clears paused; a None/unknown phase leaves it unchanged. Default off; 'LiveSplit ignores `split` while Paused' was confirmed once against a real LiveSplit (probe A11, 2026-10-30); re-check on your setup with `scripts/livesplit_probe.py --active --test-pause` before enabling. PAUSE/RESUME are phase-only, so they apply even when the index query fails on that poll; Paused->Ended clears the freeze; a safety valve (`_THAW_AFTER_FAILURES = 3` consecutive failed polls while paused, connection still up) thaws the detector with the log `LiveSplit: no answers while paused — detector unfrozen` (a later successful Paused poll re-freezes). OCR resync (`check_ocr_resync`) still runs while frozen. RESUME-side lag: a split color flash after the user resumes but before the next poll (up to `poll_seconds`) is skipped by the freeze and NOT repaired by undo/skip (LiveSplit ends up behind; a manual split is followed as a skip), so keep `poll_seconds` small with `follow_pause`. Limitation: up to ~`poll_seconds` of detection can run before the pause is observed; a split sent in that window is ignored by a paused LiveSplit and the detector sits one ahead, which the backward (undo) rule repairs after hold-off + 2 polls. When the machine becomes DONE the next LiveSplit poll is forced immediately so the non-loop exit does not wait out `poll_seconds`. NEVER send `pause`/`resume`: the server's pause starts a NotRunning timer. 
- DONE is terminal unless `--loop`: the rearm watch measures splits[0]'s color (via `TransitionDetector.first_detector`, which unlike `current_detector` survives DONE) and calls `reset()` after `detection.restart_quiet_seconds` of continuous ratio-below-`reset_threshold` frames, frame-counted at `capture.fps`. The user resets their own LiveSplit timer between runs — the detector never touches timer state, with exactly two opt-in exceptions: `start_transition.auto_start_timer: true` sends `start` when the gate fires, and `ocr.mode: undo` (per-game config, off by default, needs `--livesplit`, degrades to the dry run without it) may send `unsplit` (and `split`, only for the late-HUD recovery) via `livesplit/undo_exec.py`.
- `MpegTsFrameSource` auto-reconnects with backoff for udp/tcp/srt locations only; file locations play once then report exhausted (no replay loop). A live source that is silent for 2 s is torn down and respawned (stall watchdog) — except an `srt://...mode=listener` source before its first frame, where ffmpeg legitimately blocks until the sender connects (the watchdog re-arms once a frame has arrived).
- SRT sidecar (decoupled setup; verified end-to-end with `configs/test-white.yaml`): OBS keeps its normal Recording slot for the full-quality archive, and the **Branch Output** filter (AUR `obs-branch-output`, OBS ≥ 30.1; the AUR build fails under current GCC with `-Werror=sfinae-incomplete` unless the PKGBUILD's cmake call gets `-DCMAKE_COMPILE_WARNING_AS_ERROR=OFF`) is added to the game *scene* and streams a low-res H.264 feed to `srt://127.0.0.1:9733` from its **Streaming** section (server field; Stream Count ≥ 1 — its Recording section only writes files). UDP/`mpegts` is not available in that plugin, hence SRT. The splitter is the SRT listener: `--live "srt://127.0.0.1:9733?mode=listener&rcvlatency=20000" --width 640 --height 360` (SOURCE overrides `capture.stream_url`; width/height must equal the filter's output resolution or frames garble and fps reads ~16x too high). ffmpeg's SRT options are in **microseconds**; `rcvlatency` defaults to libsrt's ~120 ms and SRT latency is the larger of both ends' values.
  - Measured latency (clock window in OBS → `--snap 300` write time): ~594 ms at defaults → ~481 ms with `rcvlatency=20000` → ~252 ms after raising the NVENC bitrate from 100 to 1500 kbps. 100 kbps CBR at 640x360@60 costs ~230 ms of pacing delay; low-res, not low-bitrate, is what saves CPU. Keyframe interval 1 s; do not add nvenc `delay=0 zerolatency=1`.
  - Start order: start the splitter (listener) first, then enable the filter. Enabling the filter first leaves OBS retrying a dead port and the splitter waited >10 s to connect (suspected OBS retry delay; not confirmed in the OBS log). `mode=caller` on the splitter with OBS listening (`mode=listener` in the Branch Output server field) is the untested alternative that would allow leaving the filter on.
  - `capture.fps` must equal the stream's actual rate (check with `ffprobe` against the listener URL); `required_frames ≈ capture.fps / 20` still applies.
  - Known cosmetic issue: the desync WARN can fire once between a split firing and the reset clearing, because the index only advances on clear while LiveSplit has already advanced. LiveSplit ignores `start`/`split` while its timer is `Ended`, so reset the timer between `--loop` runs.
- Screen evidence / OCR (increment 1: `ocr.mode: verify_only` is the read-only mode (default; a later increment added the opt-in `mode: undo`); resync and the optional gate are NOT implemented). The previous OCR resync path never worked (frame-number equality check, a reference to the reused capture buffer, an invalid `SetImage(tolist())` call, unhandled worker exceptions) and was replaced. Now: `OcrWorker.submit_frame(frame, idx, epoch)` copies the ROI crop into a private slot buffer ON THE CAPTURE THREAD (never keep a reference to `frame`; RawPipeReader reuses it), the worker waits on an Event, runs preprocess + reader outside the lock and survives every reader exception (`status`: ok / `error: ...` / `failed` after 5 consecutive errors, it keeps trying). `poll_result()` is sticky (HUD text); `take_result()` yields each distinct reading once. `TransitionDetector.epoch` increments on EVERY state or index change; readings are stamped with it at capture time and `EvidenceFilter` (detection/evidence.py) discards epoch mismatches, readings older than `filter.max_age_seconds` (age = now frame - reading frame; never frame-number equality), confidence below `filter.min_confidence`, out-of-label-set values, and requires `filter.consensus_frames` consecutive distinct agreeing readings (`jump_consensus_frames` when the screen index is neither the detector index nor +1; any rejected reading restarts the streak). `check_ocr_resync` NEVER changes `_index`/state and nothing is sent to LiveSplit; the verdict is `machine.ocr_evidence` (AGREE/MISMATCH), evaluated only in NORMAL. Backend: `engine.backend` auto|tesseract_cli use the system `tesseract` binary (PNG on stdin, `tsv` on stdout, `OMP_THREAD_LIMIT=1`, `nice -n 10` when available, `engine.timeout_seconds` then kill); `tesserocr` is accepted by config but reports unavailable. `--check` prints `ocr backend: tesseract_cli OK (<version>)` or `ocr backend: UNAVAILABLE (<reason>)` (exit 0); `--live` prints a WARN and shows `ocr=n/a` when unavailable and keeps detecting. HUD column: `ocr=N=` agree, `ocr=N!` mismatch, `ocr=?` no consensus, `ocr=n/a`, `ocr=err`; the `OCR:` event line is rate-limited per distinct (screen, detector) pair. For single digits use `engine.whitelist: "0123456789"`. OCR hazards measured by the test pass: psm 7 (single line) is the recommended default for numbers and labels; psm 10 is Tesseract's single-character mode and read multi-digit numbers (1-20) fine at confidence 87-97 in testing on one font (LiberationSans-Bold 26px, 64x36 ROI), but that is font/size dependent and not guaranteed; psm 8/13 gave low confidence (38-72, mostly under the 60 gate); with a digit whitelist the letters "IO" can read as "10" at conf ~64; low-contrast "12/20" can read as "20"; `parse_tsv` joins words with spaces, so "1 2" resolves to split 1 with a bare `(\\d+)` pattern. Prefer anchored patterns such as `"^\\s*(\\d+)\\s*$"`. `poll_interval_frames` is only the SUBMIT cadence. `ocr.max_reads_per_second` (default 4.0, finite, >0, <=30) caps the worker: after each read it waits out the rest of 1/rate on the stop Event (close() stays prompt), latest-wins slot unchanged. Read cadence = min(submit cadence, max_reads_per_second, tesseract latency ~0.1 s); at the default a verdict (3 consensus reads) takes ~0.75 s and costs about half of a niced core (measured +~50%); raise the cap for faster confirmation. The legacy `OcrWorker(detector, poll)` constructor is uncapped; `build_ocr_worker` applies the config cap. BEHAVIOR CHANGE: existing `ocr:` configs now really spawn tesseract processes during `--live` (about one niced core); the old OCR path never ran. The `ocr = ["tesserocr"]` extra in pyproject.toml is currently UNUSED (reserved for a possible future tesserocr backend; the CLI backend needs only the `tesseract` binary). `--detect`/`--probe` shut the worker down; `--live` builds the machine immediately before the try/finally that calls `shutdown_ocr()`. The evidence TTL is `ceil(filter.max_age_seconds * capture.fps)` frames.
- OCR increments 2-3 (`ocr.undo`; with `ocr.mode: verify_only` it is a DRY RUN only: nothing is sent to LiveSplit and detector state never changes because of OCR; `ocr.mode: verify_only` + `undo:` stays this dry run; see increment 4 below for `mode: undo`). `LiveSplitClient.unsplit()` exists (fire-and-forget `unsplit\n`, like `split()`); only `livesplit/undo_exec.py` calls it (a source-grep guard test allows exactly that module). `preprocess.threshold: color` (+ `text_color: [r,g,b]` required, `text_tolerance` 0-255 default 40): after upscale/blur ONE `cv2.inRange` against the text colour (BGR bounds precomputed in `PreprocessParams.text_lo/hi` via `text_bounds`), inverted to black-on-white, padded; it ignores backgrounds/bars/polarity. Why: Otsu picks the minority class as text, so a black side bar inside the ROI (or a loose ROI) flips polarity and reads nothing. Verified on `tests/fixtures/example_hud.png` (1920x1080, level digit at x~0.105-0.135, y 0-0.055): ROI `x=0.105,y=0.0,width=0.03,height=0.055` reads '8' (conf ~97) at 1920x1080 and 640x360 (INTER_AREA); `configs/start-powerless.yaml`'s ROI (0,0,0.10,0.10) reads nothing. Death-vs-level problem: a death looks identical to the level transition, so the colour detector splits on it; the judge (`detection/undo_judge.py`, pure, injectable clock) decides afterwards whether the HUD number advanced. Terms: k = split that fired, D = k+1 = detector index after the advancing clear, S = trusted screen index. A window opens on the advancing clear in `_feed_waiting` (not the start gate, never the last split / N=1) and the machine records the fire time in `_feed_normal` plus a baseline (an AGREE for index k within `baseline_seconds` before the fire; `require_baseline` default true, else `no baseline` and no verdict). S == D -> GENUINE (logs `HUD advanced +X.XXs after split`, window closes); S == D-1 before `settle_seconds` since the FIRE -> ignored (HUD lag guard); past settle, `confirm_reads` consecutive distinct trusted reads spanning >= `confirm_seconds` -> UNDO verdict (dry run: `OCR: would UNDO split ...`; exposed as `machine.undo_target`); any untrusted/None/odd reading breaks the streak; S > D or S < D-1 -> warn once per pair, no action; any epoch change closes the window as CANCELLED, `window_seconds` after the fire as EXPIRED; one closing verdict per window. Trust for undo: `max(undo.min_confidence, engine.min_confidence)` on top of `EvidenceFilter.screen_index` (pure epoch/age/confidence/label checks; `feed` calls it). `ocr.undo` absent -> no judge, behaviour identical to before. Cost: idle = one bool test per frame in `check_ocr_resync`; the judge runs only when a NEW OCR result arrives. Status column shows `undo?` while a window is open; the generic `OCR: screen says ...` line is suppressed for the S == D-1 case while it is open. HUD-lag caveat (the biggest risk): the HUD changes AFTER the colour event with a game-dependent lag; run in dry-run, watch the `HUD advanced +X.XXs` lines and set `settle_seconds` ~1.5x the largest observed value; a genuine transition whose HUD updates later than settle+post_clear+confirm WILL be wrongly undone in `mode: undo` (then recovered by the late-HUD recovery, see increment 4). `apply_to_last_split` (default false) enables last-split coverage, see increment 5. Review-fix notes: `settle_seconds` is measured from the FIRE, `post_clear_seconds` (default 1.0) from the advancing CLEAR; a D-1 read counts only when both have elapsed (earlier reads are ignored, they do not break the streak). `window_seconds` (from the fire) should exceed the longest transition lit time + settle + confirm. `confirm_reads: 1` with `confirm_seconds: 0` is rejected. Reads are capped by `ocr.max_reads_per_second` (default 4/s), so the default confirm_reads 3 + confirm_seconds 1.0 needs ~5 reads / ~1.0-1.25 s in practice. The baseline AGREE must come from the same epoch (a reset/rollback/advance/clear bumps it). Non-finite (NaN/inf) confidences are untrusted, and huge ints give a ConfigError ('must be a number'). The OCR ROI must cover ALL digits of the highest level number with ~2 px margin (at 640x360 the strict example ROI clips the '1' of '15'; measured read '5'; with 2 px margin it reads '15'). Unknown keys in `ocr.undo` are silently ignored (a typo keeps the default). `text_color`/`text_tolerance` are ignored unless `threshold: color`. The cancel log line reads `undo window cancelled: state changed`; `--check` shows the effective confidence floor max(undo, engine, filter min_confidence). `ocr.undo` changes need a restart (hot config reload keeps the judge built at startup). the GUI does not drain judge events (queue capped at 32).
- OCR quality limits:
  OCR under low bitrate/quality (offline, ONE frame/font/synthetic motion, not real footage; see README): at 640x360 NVENC >= 200 kbps reads 20/20 (100k workable), x264 needs >= ~400 kbps (200k 18/20, 100k 10/20); 320x180 is unreadable, at 480x270 a 3x3 blur or JPEG quality <= 20 breaks it, at 640x360 a 5x5 blur does. Best tuning for white-on-gray text: `threshold: color`, `text_tolerance` ~ half the text/background contrast (70 here), `blur: 0`, `scale: 4` (36/62 vs 17-18/62 at the defaults on the 14 hardest cases). Degraded frames can produce confident WRONG digits that consensus does not catch (3 of 62 reads >= 80 with tuned settings), so keep `undo.min_confidence` >= 85 for `mode: undo` and run the dry run first.
- OCR increment 4 (`ocr.mode: undo`, the executor; CLI only, the GUI never drains judge events and must not crash). `ocr.mode` is `verify_only | undo`; `undo` needs non-empty `ocr.patterns`, uses `ocr.undo:` (absent = defaults) plus `recover_late_hud` (default true) and `recover_seconds` (finite > 0, default 10.0), and is captured once at startup. Without `--livesplit` startup prints `WARN: ocr.mode undo needs --livesplit; running as verify_only (dry run)`; with it but the server down at fire time the executor SKIPS (the detector is never rolled back alone). `--check` prints `ocr undo : ACTIVE | DRY RUN | OFF (...)` matching runtime; `mode: undo` REQUIRES `livesplit.follow_timer: true` (cross-section ConfigError `ocr.mode "undo" requires livesplit.follow_timer: true`, checked after every per-section error; `resync_on_unsplit` alone is not enough; the `verify_only` dry run does not need it), because follow_timer's rollback/skip rules repair whatever the executor could not confirm. Run the dry run first.
  - Flow: judge UNDO verdict -> `OCR: UNDO "<name>" confirmed (...)` -> `UndoExecutor.attempt(client, machine, S, now)` (`livesplit/undo_exec.py`, Protocol-typed, synchronous in the frame loop, only when a verdict exists; the verdict is consumed even when skipped = one attempt per verdict). Terms: k fired, D = k+1 detector index, S = D-1, L = LiveSplit index. Preconditions: phase Running and L == D; L == S means LiveSplit is already there (roll back only, nothing sent); any other L (a manual split gives D+1) SKIPS with a WARN. Then `unsplit()` and a verify `getsplitindex`: L == S -> `machine.apply_undo(S)` (`UNSPLIT sent -> index L (verified)`); L < S (simultaneous user unsplit) -> `apply_undo(L)` + WARN.
  - `apply_undo` = `rollback_to` guards but ALWAYS ends in WAITING_FOR_RESET with `_transition_is_start = True` (so a still-lit colour must fall below `reset_threshold` first); it closes the judge window and clears the AGREE latch. `rollback_to` is unchanged. After any detector move `_run_live` sets `last_split_time = now` (3 s UndoWatch hold-off), `undo_suppress = False`, `sync_warned = None`, `quiet_frames = 0`.
  - AMBIGUITY IS RECONCILED, NOT GUESSED. `LiveSplitClient.last_send_wrote` is True once `sendall` succeeded (an EOF in the later drain makes `unsplit()`/`split()` return False although the bytes went out); NOT_DELIVERED therefore means the bytes never left the process. If the send returned False but may have been written, the verify query got no answer, or it still shows L == D, the executor re-reads the index twice synchronously (after ~75 ms and ~275 ms) and then, if the server stays silent, from the frame loop (`pending_step`, one query per backoff step 0.5/1/2 s, 5 s deadline). L == S -> `UNSPLIT applied (confirmed late)`; L == D after the re-checks -> IGNORED (`unsplit had no effect`, detector untouched, no flip-flop with follow_timer); L < S -> `apply_undo(L)` + WARN; deadline -> `LiveSplit: could not confirm unsplit; detector at <D>, LiveSplit unknown — livesplit.follow_timer (required for ocr.mode undo) repairs it` (UNCONFIRMED). While pending, no new attempt/recovery starts and a second `unsplit` is never sent; the reconcile ends WITHOUT moving the detector if the machine epoch/state changed (follow_timer rolled it back, a genuine colour fire). A late reply to a timed-out query may be read by a later query; that only ever shows an OLDER index ("no effect"), never a wrong rollback. LiveSplit's real command ordering was checked once against a real server (probe A7, 2026-10-30: `unsplit` was applied before the next `getsplitindex` reply in 5/5 rounds, 0 ms); other versions/setups may differ, so the re-checks stay and keep the executor correct either way.
  - Late-HUD recovery (`recover_late_hud`, mode undo only): armed after ANY own undo that ends with the detector rolled back by us (verified or confirmed late; not for the already-there / simultaneous-user cases). For `recover_seconds`, with no new colour fire (epoch unchanged except the undo's own settle clear), S+1 reads that each clear the undo confidence floor (max of undo and engine `min_confidence`), reach `filter.consensus_frames` and SPAN at least `undo.confirm_seconds` trigger `recover()`: phase Running, L == S, re-read L right before sending (a user split in between: advance without sending), `split()`, verify (same ambiguity/reconcile rules; L == S+1 -> `advance_to`, L > S+1 -> `advance_to(L)` + WARN, `re-split had no effect` only when L == S after the re-checks). Logs `OCR: undo regret — HUD advanced late (+X.Xs after undo); re-splitting` (RECOVERY_SKIPPED prints `... recovery not performed`). At most one recovery per undo. The recovered split is recorded LATE by the HUD lag. Residual risk: a SYSTEMATIC misread (an 8 consistently read as 9) can still trigger a false re-split; set `recover_late_hud: false` per game if the digits are unreliable.
  - Blocking (once per death, each query/send bounded by `livesplit.timeout_seconds` T): normal attempt <= 4 x T (~1 s at T = 0.25 s with a silent-but-connected server); ambiguous attempt = 5 queries + 1 send + 0.275 s of sleeps (~1.8 s at T = 0.25 s); recovery ambiguous path 6 queries; `pending_step` blocks at most T per query with exponential backoff up to 5 s. On a 120 fps SRT/UDP feed that is 100-200 frames during which the capture pipe backs up (possible packet loss or stale latency afterwards). Measured ~0.1 s against the in-process test server; idle cost < 0.5 us/frame.
  - NOT handled / residual: multi-step undo; forward corrections beyond the recovery; the GUI; any undo of the last split unless `apply_to_last_split: true` (increment 5, below); an `unsplit` that LiveSplit applies later than the ~0.3 s synchronous window (the detector stays one ahead until follow_timer's rollback rule repairs it, normally within a couple of polls; the executor never rolls back alone); a genuine colour fire while a reconcile is pending (the reconcile is dropped, LiveSplit may be one behind; follow_timer repairs it).
  - Validator-measured limits: (a) after any UNRESOLVED offset between detector and game (two deaths closer than the ~4.2 s verdict latency, recovery disabled or a HUD later than `recover_seconds`, a late-applied unsplit that follow_timer has not yet repaired, an UNCONFIRMED hung-server reconcile) `require_baseline` makes undo inert for the rest of the run (`no baseline` on every later split) until the offset is fixed manually or by reset; (b) with `recover_late_hud: false`, or a HUD later than `recover_seconds` after the undo, LiveSplit and the detector stay one split BEHIND the game and you must fix it manually (the log only says `OCR: screen says split N ..., detector at M (no action)`); (c) latencies at 640x360/30 fps: undo ~4.1-4.2 s after the fire at defaults (settle 3.0 / post_clear 1.0 / 3 reads over 1.0 s), ~1.7 s with the fast set (1.0 / 0.5 / 0.6 s) whose false-undo ceiling is a HUD lag of ~1.7 s; the recovery split comes ~0.9 s after the HUD first reads the new level; a recovered split is recorded late by roughly the HUD lag and the unsplit+split pair does NOT restore the original timestamp; (d) the frame loop blocks ~1.0 s at a verdict against a connected-but-silent server (100-140 frames of backlog at 120 fps; no loss at 30 fps); (e) a death on the LAST level is not undone (increment 5 not implemented); (f) validated only offline/synthetic: no real OBS or real game footage (LiveSplit command semantics were checked once against a real LiveSplit with `scripts/livesplit_probe.py`), no 1080p, and `--loop` with undo, the GUI path and `--overlay` were not exercised; (g) the stale-reply hazard was only exercised in its benign shape.
  - Increment 5, undo on the LAST split (`ocr.undo.apply_to_last_split: true`, default false; sending still needs `ocr.mode: undo`, which requires `follow_timer`; `verify_only` + `undo:` logs `would UNDO` only). Premise (start-powerless): after a genuine finish the HUD level number VANISHES; after a death on the last level it keeps showing that level. When the last split fires (TRANSITION -> DONE) a judge window opens (k = N-1, D = N, same baseline gate, fire time = the fire, clear time = DONE entry, opened AFTER the DONE epoch bump so it does not self-cancel); `check_ocr_resync` feeds the judge while DONE. Rules as for other windows PLUS `ocr.undo.last_split_extra_settle_seconds` (default 2.0, finite >= 0) added to `settle_seconds` for last-split windows only, because a false undo of a genuine finish has NO recovery; `window_seconds` must exceed settle + extra + confirm when the flag is on (ConfigError). New verdict FINISHED: blank/untrusted reads that start only after settle+extra and post_clear, number `confirm_reads` and span `confirm_seconds` close the window (`OCR: HUD gone after the last split — run finished, no undo`); blank reads earlier (HUD hidden during the death screen) are ignored. Consequence: the HUD must vanish before settle + extra + post_clear + confirm (~7 s with defaults) — a HUD that lingers longer after a real finish is WRONGLY undone (documented, tested). Executor: a last-split attempt accepts phase Ended (only for these windows; Paused/NotRunning still skip) with L == N, sends ONE `unsplit`, verifies L == N-1 (Running), `apply_undo` from DONE (leaves DONE, settle state), same ambiguity/reconcile rules (pending ends if the epoch changes; follower/UndoWatch cannot double-roll back), NO late-HUD recovery: a false undo leaves LiveSplit Running at the last segment and the detector waiting for the last transition again; finish by hand and follow_timer's RUN_ENDED rule follows. Non-loop exit hold: while a last-split window is open (or a reconcile is pending) the process does NOT exit at DONE; bounded by FINISHED/CANCELLED/EXPIRED/`window_seconds` (so a genuine finish exits ~guard+confirm after the finish, about 7 s with defaults; without the flag nothing changes); after an undo from DONE the DONE state/timers reset. `--loop`: the quiet-frames rearm is HELD while a window or reconcile is open (simplest safe choice); a reset/rearm after that cancels as usual. `--check` shows `last-split=ON(+Ns settle, exit held up to Ws)`. Status: validated offline/synthetic (in-process stateful fake LiveSplit with Ended -> Running via unsplit); a real LiveSplit's Ended -> Running through `unsplit` and its apply latency were confirmed once with `scripts/livesplit_probe.py` (A6/A7, 2026-10-30), but not against real game footage. Run the dry run first.  After ANY last-split `unsplit` attempt (even one reported as having no effect or unconfirmed) the non-loop DONE exit also waits for a LiveSplit phase polled at least `poll_seconds + timeout_seconds` AFTER the send, because LiveSplit may apply the unsplit later than the ~0.3 s re-checks and the cached phase may still read Ended; if that fresh phase is Running the process keeps running and follow_timer's rollback repairs the detector. The wait is bounded (6 x poll_seconds + 4 x timeout_seconds + 3 s) and skipped when LiveSplit is unreachable, so a hung server still lets the process exit; apply_to_last_split off, dry runs and FINISHED (nothing sent) exit as before. Honest notes: (a) the judge measures settle/post_clear/confirm with the clock at PROCESSING time, not the reading's capture time; if the main loop stalls for seconds after DONE (LiveSplit queries timing out, a backlogged pipe) a HUD that really lingers ~1.5 s of video time can age past the ~6 s guard and be wrongly undone — low in practice (confirm_seconds needs wall-clock time between reads and the worker keeps only the latest frame), but it is a second path from a genuine finish to a false undo besides the documented lingering-HUD limit; (b) ANCHORED `ocr.patterns` (`^...$`, e.g. `"^\\s*(\\d+)\\s*$"`) are required in practice for `apply_to_last_split`: end-card/menu text containing a number would otherwise count as a trusted HUD read (startup and `--check` print a non-fatal `WARN: ocr.patterns "<regex>" is not anchored` for `mode: undo` or `apply_to_last_split`); (c) with `--loop` the quiet-frames rearm is held while a last-split window is open (up to `window_seconds`): if the HUD never disappears and a new run starts within that time, its first split is ignored while the machine is still in DONE.
  - Tuning workflow: run `mode: verify_only` + `undo:` (dry run) first, watch `OCR: HUD advanced +X.XXs after split`, set `settle_seconds` ~1.5x the largest lag; measured with defaults (settle 3.0 / post_clear 1.0 / confirm 3 reads + 1.0 s) a 2.8 s lag was fine and a 4.5 s lag produced a false undo ~4.2 s after the fire. ## Multi-Agent Development Protocol

Phases 1–7 are the established project baseline.

Do not rewrite or refactor completed phases unless the current task explicitly
requires it and the orchestrator has approved the architectural change.

Every non-trivial change should follow:

1. Explorer — understand the existing implementation.
2. Researcher — investigate external dependencies or unknown technical behavior
   when necessary.
3. Architect — determine the smallest safe architectural change.
4. Implementer — implement only the approved design.
5. Test Engineer — attempt to break the implementation.
6. Reviewer — independently review the implementation.
7. Integration Validator — validate the runtime pipeline when applicable.

The implementer must not approve its own implementation.

### Baseline protection

- Preserve existing behavior unless the task explicitly changes it.
- Do not remove or weaken existing tests.
- Do not perform unrelated refactors.
- Do not introduce dependencies without justification.
- Do not change public interfaces without architectural justification.
- Treat phase documentation as authoritative.

### Required verification

For production-code changes, run:

    uv run pytest -v
    uvx ruff check .
    uv run basedpyright src tests
    uv run python -m autosplitter.main --check

Then run the applicable phase/demo or integration command.

### Visual detection requirements

Changes to detection behavior should include positive, negative,
tolerance-boundary, debounce, hysteresis/reset, and duplicate-split cases.

### Capture requirements

Changes to capture must consider partial reads, EOF, reconnect behavior,
resolution mismatch, frame-rate stability, packet loss, and decoder startup.

### LiveSplit requirements

Changes to LiveSplit integration must consider unavailable-server,
reconnect, `split\n`, duplicate-split, and desynchronization behavior.

### Performance requirements

The frame-processing hot path is performance-sensitive.

- Keep ROI cropping before image processing.
- Keep per-frame processing allocation-free where practical.
- Do not introduce per-pixel Python loops.
- Do not trade sustained capture FPS for unnecessary abstraction.
- Performance-sensitive changes should include before/after measurements.

### Agent permissions

Read-only agents must not modify production code.
The reviewer is independent of the implementer and must not silently repair
the implementation while reviewing it.
